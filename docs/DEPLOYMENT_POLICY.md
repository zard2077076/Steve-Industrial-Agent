# Deployment policy

`DeploymentPolicy` is immutable loader-neutral data. It explicitly bounds environment and canonical roots, affected blocks, bounding volume, route length, material cost, rotational stress, world mutations, adapters, implementations, recipe types, dimensions, time, approval expiry, backup, dry-run, human approval, rollback, block protection, claim permission, resource source and existing-machine reuse.

The formal-player-world default is preview-only: execution is disabled, mutation budget is zero, backup and human approval are required, unknown replacement/player-built blocks/block entities are protected, claim permission is required, automatic resource withdrawal is forbidden, existing-machine reuse is forbidden and destructive rollback is forbidden. Missing fields never relax the policy.

Only repository-owned isolated tests currently have an executable policy factory, and it requires both an allowed root and a separately supplied forbidden root. Even there, PW-03 requires current approval, verified backup, fresh snapshot, exact region authorization and a valid mutation budget before it can produce an internal write permit.

PW-04 evaluates these limits during preview without granting authority. Violations such as environment/root mismatch, area/volume/route/material/stress/mutation overflow, disallowed Adapter/implementation/recipe type, protected replacement, block-entity replacement, undeclared route/power materials or unsupported rollback are included in the preview and its hash. Requirements such as human approval, verified backup, region authorization, fresh snapshot, rollback and claim permission remain separate required-approval entries; their presence in a preview is not evidence that they were satisfied.

PW-05 risk assessment is also policy evidence, not approval. The five severity levels and 22 category rules are fixed in code. Every CRITICAL finding blocks approval by invariant; callers cannot supply severity or override the blocking bit. UNKNOWN, DENIED and NOT_INSTALLED permission evidence all remain critical until PW-10 supplies an authoritative exact-region ALLOWED result.

PW-06 turns the preview estimates and bounded read-only capacity observations into a separate `DeploymentBudget`. It records raw, intermediate, construction, power, logistics, input and output quantities; rotational stress and capacity margin; runtime/construction ticks; the policy maximum affected blocks; and rollback/journal storage. Violations are typed and canonically ordered. `TEST_FIXTURE_PROVIDED`, `PLAYER_PROVIDED_READ_ONLY_SNAPSHOT`, `DESIGNATED_CONTAINER`, `EXISTING_NETWORK_READ_ONLY`, `AUTO_WITHDRAW_FORBIDDEN` and `UNSUPPORTED_SOURCE` are the complete source-policy set. A budget never reserves resources, and formal-world modeling permits no automatic withdrawal.

PW-07 adds exact region authorization evidence. A request must stay inside the bound, use only its allowed typed operations, remain within the mutation ceiling and match environment, world, dimension, optional owner, preview hash, world snapshot and runtime exactly while the record is current, approved, active and unused when one-time. A passing comparison still does not produce a write permit. Formal/unknown/forbidden records cannot be approved and can contain only `READ_ONLY_SCAN`/`DRY_RUN` with zero mutations; every formal live check fails independently.

PW-08 approval is a one-time structured token, not a boolean. The current request must equal its environment, preview hash, world/snapshot/runtime/reload identity, region, target, quantity, mutation budget and entire `DeploymentPolicy`, and the decision must be APPROVED and unexpired. The gate atomically consumes the token hash once but cannot issue or upgrade a token. Tests use only the literal `TEST_ONLY` authorizer in isolated scope; that token cannot be constructed for or copied to a formal environment.

PW-09 backup execution is restricted to an explicit isolated-root/backup-root/forbidden-root path policy and `APPROVED_TEST_ONLY`. The plan must carry a complete valid canonical manifest, sufficient observed and live capacity, fixed staging/atomicity and quiesced-consistency strategies, a complete restore drill, safe staging cleanup, retention and exact journal identity. Non-isolated environment fails before path resolution. Formal backup remains model-only future work and requires a separate explicit human approval stage; no current service method can back it up.

PW-10 permission has four non-interchangeable states. Only VERIFIED `ALLOWED` evidence whose generation/fingerprint/time match its complete query may report construction permission, and that helper still refuses formal/unknown/forbidden environments. `UNKNOWN`, `DENIED` and `NOT_INSTALLED` all block. A generic ClaimAdapter response does not bypass exact region authorization or PW-11; detected third-party mods remain unsupported until a versioned Adapter is separately reviewed and tested.

PW-11 applies the complete policy again inside its independent twenty-five-check aggregation gate. It requires exact current equality across the physical plan, graph, preview, policy, region, approval, backup, permission and runtime identities and refuses every formal/unknown/forbidden environment before readiness. Its isolated `DeploymentReadyPlan` is audit evidence only and cannot be treated as a write permit, resource reservation or executable session.

PW-12 command policy is narrower still: every command is a dry-run, accepts no coordinates, approval token, backup path, resource source or execution switch, and stops before readiness construction. It reports current bounds/material/power estimates and the missing authorization/backup gates. Its independent environment marker may identify only an expected isolated fixture; no command-line option can enable `TEST_ONLY` approval or formal execution.
